# 酒店预订与入住系统需求说明

## 0. 文档概述

### 0.1 原始需求

开发一个包含预订功能、订单查询、办理入住的前后端酒店系统。

### 0.2 目标

建设一个可演示酒店核心业务闭环的系统，使顾客能够查询可订房型、提交预订并查询订单，使酒店前台能够查询订单并为符合条件的订单办理入住。

### 0.3 合理假设

由于原始需求未明确以下事项，MVP 采用这些假设：

- 系统仅服务一家酒店，但数据模型保留酒店标识。
- 顾客无须注册或登录，通过订单号与预订手机号查询订单。
- 酒店前台通过已登录的后台账号操作；MVP 仅设一种“前台人员”权限。
- 预订提交即成功，不包含在线支付、到店支付处理或担保规则。
- 以房型而非具体房号进行预订；办理入住只更新订单状态，不分配实体房间或制作房卡。
- 房价采用房型固定每晚价格；总价为每晚单价 × 入住晚数 × 房间数，不考虑税费、服务费、优惠及日期浮动价。
- 库存按“房型 + 营业日期”管理；入住日占用库存，离店日不占用库存。
- 日期以酒店所在时区的自然日为准；MVP 不处理跨时区问题。
- MVP 不实现取消订单和办理离店的操作入口，但订单模型可预留相应状态。

## 1. 用户角色

### 1.1 顾客

- 查询指定入住日期、离店日期和房间数下的可订房型。
- 查看房型基本信息和价格。
- 填写入住人与联系方式并提交预订。
- 使用订单号和预订手机号查询自己的订单。

### 1.2 酒店前台人员

- 登录后台。
- 按订单号或预订手机号查询订单。
- 查看订单详情和当前状态。
- 对符合条件的订单办理入住。

## 2. 核心业务流程

### 2.1 顾客预订流程

1. 顾客选择入住日期、离店日期和房间数。
2. 系统校验查询条件，并展示整个入住区间每天库存均充足的可订房型。
3. 顾客选择房型，填写入住人姓名和手机号。
4. 系统再次校验酒店、房型、日期和每天库存。
5. 系统一次性扣减入住区间内每天的库存并创建订单。
6. 系统展示订单号、入住信息、金额和订单状态。

### 2.2 顾客查询订单流程

1. 顾客输入订单号和预订手机号。
2. 系统校验二者是否与同一订单匹配。
3. 匹配成功则展示订单详情；否则返回统一的未找到提示。

### 2.3 前台办理入住流程

1. 前台人员登录后台并查询订单。
2. 系统展示订单详情和状态。
3. 前台核对顾客信息并发起办理入住。
4. 系统校验订单存在、状态为“已预订”，且当前日期符合入住日期规则。
5. 系统将订单状态更新为“已入住”，记录操作时间并返回结果。

## 3. 功能需求

### FR-01 查询可订房型

**需求说明**

- 顾客输入入住日期、离店日期和房间数后，可查询可订房型。
- 结果至少展示房型名称、床型、可住人数、描述、每晚单价和本次预计总价。
- 仅展示入住区间内每个营业日的可用库存均不少于所需房间数的有效房型。
- 系统应对非法日期、非正整数房间数等输入给出明确提示。

**验收标准**

1. 给定离店日期晚于入住日期、房间数为正整数且某房型每天库存充足时，该房型出现在结果中。
2. 给定入住区间任意一天库存不足时，该房型不出现在结果中。
3. 给定离店日期不晚于入住日期时，系统拒绝查询并提示日期范围无效。
4. 给定房间数小于 1 或不是整数时，系统拒绝查询并提示房间数无效。
5. 预计总价等于房型每晚单价 × 晚数 × 房间数。

### FR-02 创建预订

**需求说明**

- 顾客可基于查询结果选择房型并提交预订。
- 必填信息包括房型、入住日期、离店日期、房间数、入住人姓名和手机号。
- 创建订单时系统必须重新校验房型有效性及整个入住区间库存，不依赖此前查询结果。
- 预订成功后生成全局唯一且不可变的订单号，订单初始状态为“已预订（BOOKED）”。
- 订单保存酒店、房型、每晚单价等关键快照信息。
- 预订成功时一次性扣减入住区间内每天的对应库存；任意一天不满足时，订单创建和所有库存扣减均失败。

**验收标准**

1. 给定所有必填信息合法且每天库存充足时，系统创建一张 BOOKED 订单并返回唯一订单号。
2. 创建成功后，入住日至离店日前一天的每天可用库存均减少所订房间数，离店日库存不变。
3. 给定区间任意一天库存不足时，系统不创建订单，所有日期库存均保持不变，并提示库存不足。
4. 给定无效或停用房型时，系统拒绝创建订单。
5. 姓名为空、手机号为空或格式不合法时，系统拒绝创建订单并指出对应字段。
6. 订单总金额按快照单价 × 晚数 × 房间数计算，后续修改房型名称或价格不改变历史订单展示。
7. 多个请求并发预订同一库存时，成功订单占用量不超过库存，系统不得超卖。

### FR-03 顾客查询订单

**需求说明**

- 顾客通过订单号与预订手机号组合查询订单。
- 查询成功后展示订单号、酒店、房型、入住人、脱敏手机号、入住及离店日期、房间数、晚数、总金额、订单状态和创建时间。
- 为避免泄露订单信息，订单号不存在与手机号不匹配使用相同的失败提示。

**验收标准**

1. 输入匹配的订单号和手机号时，系统返回对应订单完整的允许展示信息。
2. 订单号不存在或手机号不匹配时，系统均提示“未找到匹配订单”，且不返回订单详情。
3. 查询操作不改变订单状态、库存或其他业务数据。
4. 展示的手机号经过脱敏，不完整暴露顾客联系方式。

### FR-04 前台登录

**需求说明**

- 前台人员通过账号和密码登录后台。
- 未登录用户不得访问后台订单查询和办理入住功能。
- 登录失败时不应透露账号是否存在。

**验收标准**

1. 使用有效账号和正确密码可登录并进入后台。
2. 账号或密码错误时均返回统一的登录失败提示。
3. 未登录访问后台受保护功能时，系统拒绝访问并引导登录。
4. 退出登录后，原会话不能继续访问受保护功能。

### FR-05 前台查询订单

**需求说明**

- 已登录前台可按完整订单号精确查询，或按完整预订手机号查询订单。
- 查询结果展示办理入住所需的订单详情及当前状态。
- 手机号可能对应多张订单，结果按创建时间倒序展示。

**验收标准**

1. 输入存在的订单号时，系统返回唯一对应订单。
2. 输入存在的手机号时，系统返回该手机号下的全部订单，并按创建时间倒序排列。
3. 无匹配数据时，系统展示空结果提示，不报系统错误。
4. 未登录用户调用查询功能时被拒绝。

### FR-06 办理入住

**需求说明**

- 已登录前台可为状态为 BOOKED 的订单办理入住。
- MVP 允许在计划入住日当天及之后办理入住，但当前日期不得早于计划入住日，也不得达到或晚于计划离店日。
- 办理成功后订单状态变为“已入住（CHECKED_IN）”，并记录入住办理时间。
- 重复请求不得导致重复状态变更或重复业务副作用。

**验收标准**

1. 订单存在、状态为 BOOKED，且计划入住日 ≤ 当前酒店日期 < 计划离店日时，办理成功并变为 CHECKED_IN。
2. 当前日期早于计划入住日时，系统拒绝办理并提示尚未到入住日期。
3. 当前日期达到或晚于计划离店日时，系统拒绝办理并提示订单已过入住有效期。
4. 订单不存在时，系统返回未找到提示。
5. 对 CHECKED_IN 或其他非 BOOKED 状态订单再次办理时，系统拒绝操作，且状态保持不变。
6. 未登录用户发起办理入住时，系统拒绝访问。
7. 办理入住不再次扣减或返还库存。

## 4. 非功能需求

### 4.1 一致性与并发

- 订单创建与整个日期区间的库存扣减必须具备原子性。
- 并发预订不得造成任何营业日库存为负数或出现超卖。
- 订单状态变更必须校验当前状态，避免并发重复办理。

### 4.2 安全与隐私

- 后台功能必须经过身份认证。
- 密码不得明文存储或在日志中输出。
- 顾客查询订单必须同时验证订单号和手机号。
- 前端展示及服务日志应避免暴露完整手机号等敏感信息。
- 所有输入应进行服务端校验，错误响应不得包含堆栈、数据库结构等内部信息。

### 4.3 性能

- 在 Demo 目标数据量（房型不超过 100 个、订单不超过 10 万条）下，95% 的可订房型查询和订单查询应在 2 秒内返回。
- 在相同条件下，95% 的创建预订和办理入住请求应在 3 秒内返回。

### 4.4 可用性

- 页面应清晰展示加载中、无结果、成功和失败状态。
- 表单校验信息应靠近对应字段，并保留用户已填写的其他合法内容。
- 关键操作结果应提供可理解、可继续处理的提示。

### 4.5 可追溯性

- 订单至少记录创建时间、更新时间和状态。
- 办理入住记录操作时间；后台操作应能识别操作人员。
- 关键失败应记录可排查的日志，但不得记录明文密码或完整敏感信息。

### 4.6 兼容性

- Web 页面应支持当前主流桌面版 Chrome 和 Edge 的最新稳定版本。
- 顾客端核心流程应能在常见手机屏幕宽度下正常使用。

## 5. 业务规则

### BR-01 日期与晚数

- 离店日期必须晚于入住日期。
- 入住晚数 = 离店日期 - 入住日期。
- 入住日期可为酒店当前日期或未来日期，不允许创建入住日期早于当前日期的预订。
- 占用库存的日期为 `[入住日期, 离店日期)`，离店日期不占库存。

### BR-02 库存

- 库存粒度为“房型 + 营业日期”，不得用房型单一静态库存代表整个日期范围。
- 预订要求区间内每一天的可用库存均不少于房间数。
- 库存扣减遵循全有或全无原则，不允许部分日期成功。
- 并发扣减后可用库存不得小于 0。

### BR-03 金额

- 每晚单价和总金额均不得为负数。
- MVP 总金额 = 每晚单价快照 × 晚数 × 房间数。
- 已创建订单的快照和总金额不随房型资料或当前价格变化。

### BR-04 订单

- 订单号全局唯一，创建后不可修改。
- 初始状态为 BOOKED。
- 本期允许的状态迁移仅为 `BOOKED -> CHECKED_IN`。
- 状态预留 CHECKED_OUT 和 CANCELLED，但 MVP 不提供进入这两种状态的业务功能。
- 禁止从 CHECKED_IN、CHECKED_OUT 或 CANCELLED 回退到 BOOKED。

### BR-05 入住

- 只有 BOOKED 订单可办理入住。
- 办理日期须满足计划入住日 ≤ 酒店当前日期 < 计划离店日。
- 办理入住不改变已占用库存。
- 同一订单最多成功办理一次入住。

### BR-06 顾客信息

- 入住人姓名为必填项，去除首尾空格后不得为空。
- 手机号为必填项；MVP 按中国大陆 11 位手机号格式校验。
- 手机号用于顾客订单查询校验，查询时须与订单留存号码完全匹配。

## 6. 异常场景

| 场景 | 系统处理 |
| --- | --- |
| 离店日期不晚于入住日期 | 拒绝请求并提示正确日期规则 |
| 入住日期早于当前日期 | 拒绝创建预订 |
| 房间数为空、非整数或小于 1 | 拒绝请求并提示修正 |
| 房型不存在或已停用 | 拒绝预订并提示房型不可用 |
| 查询后、提交前库存被其他订单占用 | 提交时重新校验；库存不足则整单失败 |
| 多人同时抢订最后库存 | 仅允许库存条件满足的请求成功，其他请求提示库存不足 |
| 库存扣减过程中发生系统错误 | 回滚全部库存变更，不创建订单 |
| 订单创建成功但响应中断 | 保留已成功订单；通过订单查询确认结果，系统不得重复扣减同一成功请求 |
| 顾客查询的订单号不存在或手机号不匹配 | 返回统一的未找到提示，不泄露订单是否存在 |
| 前台会话失效 | 拒绝后台操作并引导重新登录 |
| 办理入住时订单不存在 | 返回未找到提示，不创建任何数据 |
| 办理入住日期过早或过晚 | 拒绝状态变更并说明原因 |
| 重复或并发办理同一订单入住 | 最多一个请求成功，订单最终保持 CHECKED_IN |
| 网络或服务异常 | 页面保留可保留的输入，提示稍后重试；不得展示内部异常细节 |

## 7. MVP 范围

- 单酒店基本信息和房型展示。
- 按入住日期、离店日期、房间数查询可订房型。
- 按日期管理房型库存并防止并发超卖。
- 顾客填写入住人信息并创建预订。
- 订单金额计算、关键资料快照和 BOOKED 状态。
- 顾客使用订单号与手机号查询订单。
- 前台账号登录、退出和受保护访问。
- 前台按订单号或手机号查询订单。
- 前台为符合规则的 BOOKED 订单办理入住。
- 基础输入校验、错误提示、日志与响应式页面。

## 8. 暂不实现的功能

- 顾客注册、登录、会员、积分及常用入住人。
- 多酒店、门店切换、集团管理。
- 在线支付、退款、发票、押金和担保。
- 订单取消、修改、续住、提前离店及办理退房。
- 实体房间/房号分配、排房、换房和房卡管理。
- 动态价格、价码、套餐、促销、优惠券、税费和服务费。
- 早餐、加床、儿童、宠物等附加商品或入住政策。
- 短信、邮件、站内消息等通知。
- 渠道分销、第三方平台同步和库存共享。
- 前台以外的细粒度角色权限、审批和完整审计后台。
- 数据报表、经营分析和财务对账。
- 候补、超售、团体预订和钟点房。
- 国际手机号、多语言、多币种和跨时区处理。

## 9. MVP 验收标准

### 9.1 端到端业务验收

1. 在某房型连续三天每天可用库存为 2 的前提下，顾客预订 1 间、入住三晚成功；系统生成 BOOKED 订单，相应三天库存各减 1，离店日库存不变。
2. 顾客使用正确订单号和手机号可以查看该订单；使用错误手机号无法看到订单详情。
3. 已登录前台可以通过订单号找到该订单，并在入住日当天将其状态从 BOOKED 更新为 CHECKED_IN。
4. 前台再次对该订单办理入住时操作失败，订单仍为 CHECKED_IN，库存不发生变化。
5. 当入住区间中任意一天库存为 0 时，预订失败，不产生订单，其他日期库存不变化。
6. 当两个并发请求争抢最后一间库存时，最多一个预订成功，任何日期库存均不为负数。

### 9.2 功能完整性验收

- FR-01 至 FR-06 的全部验收标准均通过。
- 顾客端和前台端均具备加载、成功、空结果及失败反馈。
- 所有受保护的后台功能在未登录状态下均不可访问。

### 9.3 质量验收

- 关键业务规则具备可重复执行的测试，至少覆盖正常流程、库存不足、非法日期、并发超卖、查询鉴权、非法状态和重复入住。
- 不存在可导致库存为负、部分日期扣减或非法订单状态迁移的已知缺陷。
- 达到第 4 节定义的性能、安全、可用性、可追溯性和兼容性要求。
